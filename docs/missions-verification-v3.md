# Mission verification record — A13, V3 missions (M09–M12)

Acceptance A13 (spec §14.2): in a fresh environment the starter installs,
baseline checks pass, mission checks fail **for the intended reason**, and the
reference solution passes both.

Verified 2026-09-10. Every number below is captured from a real run on this
machine.

## Environment

.NET SDK 10.0.302, pinned in each mission's `global.json` with
`rollForward: latestFeature`. It is the only SDK installed here, so no version
mismatch was possible.

PostgreSQL 18 on `127.0.0.1:5440`. Each mission owns its own database:

| Database | Mission |
| --- | --- |
| `m09_supportdesk_test` | M09 |
| `m10_efcore_test` | M10 |
| `m11_inventory_test` | M11 |
| `m12_reports_test` | M12 |

All four are separate from the platform's `devpractice` / `devpractice_test`
(spec §5.2). **Each was dropped and recreated empty before its mission was
verified.**

### "Migrations apply to an empty database" reads differently here

These four missions have **no EF Core migrations**. The schema is created with
`EnsureCreatedAsync`, called by each test fixture (and by `tools/SeedRunner` in
M09). That is a deliberate design choice — migrations are the subject of .NET
chapter 6 and of M10's reading-the-SQL work, not of the harness — but it means
A13's wording has to be read honestly: what was proved is **`EnsureCreated`
against an empty database, then the suite run twice**, not that a migration
applied. Where a mission's baseline asserts the seed is repeatable, the baseline
suite was run twice in a row against the same database and passed both times.

## A defect found and fixed first: the missions could not be built at all

None of the four starters had a `.sln`, and no `.csproj` sat directly in
`starter/`. Each holds two or three sibling project directories instead
(`src/…`, `tests/…`, and for M09 `tools/SeedRunner`). The .NET CLI looks for a
project or solution file in the **current directory only**, so the commands every
mission documents —

```
dotnet restore
dotnet build
dotnet test --filter Category=Baseline
```

— would have failed immediately with "no project or solution file found". The
mission text was not wrong about what a learner should type; there was simply
nothing for those commands to act on.

A solution file was added to each starter (`SupportDesk.sln`, `SupportDesk.sln`,
`Inventory.sln`, `Reports.sln`), listing that mission's projects with stable
GUIDs. Nothing else changed, and no test or assignment file was touched. The
restore logs below are the proof it worked: each project restored **through the
solution**.

Around 350 MB of committed `bin/` and `obj/` build output was also removed from
the four starters. It was stale compiler output from an interrupted earlier
session, it is regenerated by `dotnet build`, and it would have been shipped
inside the release asset bundles.

## A finding that was recorded rather than fixed: NU1903

Every restore and build of these four missions prints, repeatedly:

```
warning NU1903: Package 'System.Security.Cryptography.Xml' 9.0.0 has a known
high severity vulnerability
```

It arrives transitively through `Microsoft.NET.Test.Sdk` 17.11.1. It is a
**test-only** dependency and is not part of the API a learner runs or deploys.
It was not silenced. The honest fix is to move the test SDK forward and re-run
A13 for all four missions, and that has not been done, so it is recorded here and
in `known-limitations.md` instead of being hidden behind `NoWarn`.

## M12 — the same job, cancelled and rerun, in .NET — A13 VERIFIED (after one check was strengthened)

Verified 2026-09-11. This mission needed two passes, because the suite as
shipped had a mission check that already passed on the starter. Both passes are
recorded; the second is the one A13 rests on.

### First pass — the suite as shipped

| Stage | Command | Result |
| --- | --- | --- |
| Restore | `dotnet restore` | exit 0; both projects restored through `Reports.sln` (17.1 s each) |
| Build | `dotnet build --no-restore` | **0 errors**, 8 warnings (all NU1903), 3m54s |
| Baseline (starter), run 1 | `dotnet test --filter Category=Baseline` | **3/3 passed**, exit 0 |
| Baseline (starter), run 2 | same | **3/3 passed**, exit 0 — repeatable |
| Mission (starter) | `dotnet test --filter Category=Mission` | **2 failed / 1 passed**, exit 1 |
| Build (solution) | `dotnet build --no-restore` | **0 errors**, 2m18s |
| Baseline (solution) | `dotnet test --filter Category=Baseline` | **3/3 passed**, exit 0 |
| Mission (solution) | `dotnet test --filter Category=Mission` | **3/3 passed**, exit 0 |

The two failures are the intended reason. The outer message is EF Core's
generic `DbUpdateException : An error occurred while saving the entity changes`,
which on its own proves nothing; the inner exception, read from the unfiltered
test output, is:

```
---- Npgsql.PostgresException : 23505: duplicate key value violates unique
     constraint "IX_Rows_JobId_ItemKey"
   at Reports.Api.ReportRunner.RunAsync(Guid jobId, CancellationToken ct)
      in ...\starter\src\Reports.Api\ReportRunner.cs:line 67
```

for both `a_rerun_after_a_partial_failure_does_not_duplicate_committed_effects`
and `a_rerun_of_a_finished_job_is_a_no_op`. That is the unique index on
(`JobId`, `ItemKey`) doing exactly what the mission text says it is there for:
the starter's rerun repeats work it already committed, and the database turns
silent duplication into a loud failure. It is not a connection error and not a
missing table. (The outer-only view produced by the verification script's
`grep` was not enough to say this; the starter was rebuilt and the mission
checks rerun with full output to get the inner text, and the counts were the
same: 2 failed / 1 passed.)

The check that passed on the starter was `cancellation_is_observed_partway_through`,
and that is the problem.

### The cancellation check as shipped did not exercise what it asserted

The starter's `RunAsync` takes a `CancellationToken` and never checks it — that
is the mission's first defect. The shipped check cancelled the token
(`CancelAfter(1 ms)`, then `Task.Delay(30)`) **before** calling `RunAsync`, and
asserted that `OperationCanceledException` escaped and fewer than five rows were
written.

The innocent mechanism: the starter threads `ct` into its very first statement,
`db.Jobs.FirstOrDefaultAsync(..., ct)`, and into every `SaveChangesAsync(ct)`.
EF Core and Npgsql observe an already-cancelled token on that first query and
throw before the runner's loop has run at all. Zero rows, exception escapes,
both assertions satisfied — by the driver, not by the runner. The check could not
tell a runner that stops at item boundaries from one that never looks at the
token. It is a fifth instance of the pattern in `handoff/04-gotchas.md`,
"tests that assert behaviour they never exercise": green, certifying nothing.

The check was **strengthened**, not weakened, and nothing else in the suite was
touched. Same name, same `[Trait("Category", "Mission")]`. The new body cancels
the token from **inside** the loop, through the existing `FailOn` hook, while the
third item (`ferry-lane-cafe`) is being processed, and asserts all three of:

1. `OperationCanceledException` escapes `RunAsync`;
2. exactly **3** rows are committed — the third item completes, the fourth never
   starts; a whole number of finished items, never a torn write;
3. the job is left **`Queued`**, not `Failed`, with its committed effects intact
   and ready to resume.

The third assertion is the discriminating one. The starter's `catch (Exception)`
marks a cancelled job `Failed`; the solution's `catch (OperationCanceledException)`
puts it back on the queue.

### Second pass — the strengthened suite

| Stage | Command | Result |
| --- | --- | --- |
| Build (starter) | `dotnet build --no-restore` | **0 errors**, 8 warnings (NU1903), 3m00s |
| Mission (starter) | `dotnet test --filter Category=Mission` | **3 failed / 0 passed**, exit 1 |
| Build (solution) | `dotnet build --no-restore` | **0 errors**, 6m17s |
| Mission (solution) | `dotnet test --filter Category=Mission` | **3/3 passed**, exit 0 |
| Baseline (solution) | `dotnet test --filter Category=Baseline` | **3/3 passed**, exit 0 — no regression |

The strengthened check now fails on the starter exactly where it should:

```
cancellation_is_observed_partway_through
   Assert.Equal() Failure: Values differ
Expected: Queued
Actual:   Failed
   at Reports.Tests.MissionTests.cancellation_is_observed_partway_through()
      in ...	ests\Reports.Tests\MissionTests.cs:line 51
```

The first two assertions passed on the starter (the driver threw on the
cancelled token during the third item's save, and the starter's catch block
flushed that third row), and the job-state assertion failed. The other two checks
failed with the same `23505` unique-violation as before. Before/after on the
starter: **2 failed / 1 passed → 3 failed / 0 passed**. On the solution: 3/3
both times.

Which criteria are exercised by a failing-then-passing check, and which are not:

| Criterion | Exercised by |
| --- | --- |
| A rerun after a partial failure does not repeat committed effects | `a_rerun_after_a_partial_failure_does_not_duplicate_committed_effects` — fails, then passes |
| A rerun of a finished job is a no-op | `a_rerun_of_a_finished_job_is_a_no_op` — fails, then passes |
| Cancellation is observed by the runner, at an item boundary, and the job is requeued | `cancellation_is_observed_partway_through` — **after strengthening**: fails, then passes |
| Cancellation under a real host shutdown | prose only — see "Not verified" |

The baseline's third check — the unique index rejects the same item twice — is
the one worth noting, as with M11: it proves the backstop works before the
learner starts, so the mission is "stop relying on the backstop", not "add one".

After the second pass the starter's `ReportRunner.cs` was restored from the
backup taken before the solution was copied in, confirmed to differ from the
solution file, and the starter was rebuilt so the compiled assembly matches the
starter source. The strengthened `MissionTests.cs` changes the starter bundle, so
the `m12-dotnet-background-compare-starter-v3` checksum in `release-v3.json` was
recomputed with `dp-content assets` and updated.

Two small observations, not defects: each build here printed **8** NU1903
warnings, not the 16 seen for M09; and the first run's verification script
never rebuilt after restoring the starter source, so for a while the starter's
`bin/` held the solution's assembly. Any `--no-build` test run in that window
would have reported the solution's result under the starter's name. The rebuild
in the second pass, and the final rebuild after restore, close that gap.

## Not verified

- **M09's "the React frontend works unchanged".** This is an acceptance criterion
  of the mission and a learner checklist item, and no automated check covers it.
  M01's React app was not started against the .NET API during this verification.
  The contract is pinned by the mission tests, which is evidence about the server,
  not about the client.
- **`dotnet run`** for any of the four APIs. Only `dotnet build` and `dotnet test`
  were executed. The `ASPNETCORE_URLS` values in each `.env.example` are therefore
  documented, not exercised.
- **M09's `tools/SeedRunner`.** It is referenced by the README as a convenience
  for local play and by no check command, so it was restored and built but never
  run.
- **Any `.env` loading.** .NET does not read a `.env` file here, and nothing in
  these missions adds a loader. Verification set the connection environment
  variables explicitly; a learner relying on the defaults baked into the code gets
  the same databases.
- **Cancellation under a real host shutdown** in M12. The mission checks cancel a
  token directly, which is the mechanism, but no run was interrupted by stopping
  the hosted service itself.
